# Phase 2A — الأداء

## ما هو مضمون فعليًا بالبناء (Verified by construction)

- **لا حلقة نداءات HTTP لكل صفحة/قسم/حقل عند تحميل الاستوديو**: تحميل الاستوديو يستدعي نداءَي HTTP فقط بالضبط — `GET /forms/{formId}` و`GET /forms/{formId}/versions/{versionId}` (`FormQueryService.GetDetailAsync` و`FormVersionService.GetAsync`، كلاهما موجود مسبقًا ولم يتغيّر). الـSchema بأكمله يصل كنص JSON واحد ضمن `FormVersionDetailDto.DraftSchemaJson` ضمن هذين النداءين، ثم يُحلَّل ويُعاد بناؤه بالكامل في الذاكرة على الواجهة — لا نداء HTTP إضافي لكل عنصر. **هذا لا يعني بالضرورة استعلامَي EF Core فقط على مستوى قاعدة البيانات** — كل من `GetDetailAsync`/`GetAsync` قد ينفذ أكثر من استعلام EF Core داخليًا (Includes، فحوصات نطاق/صلاحية منفصلة)؛ عدد استعلامات EF Core الفعلي لم يُقَس (انظر "اختبار Query-count budget آلي" أدناه)، فادعاء عدم وجود N+1 مقصور على مستوى نداءات HTTP، لا على مستوى قاعدة البيانات.
- **Outline وCanvas يستخدمان نفس الحالة**: كلاهما يقرأ من `history.present` (نفس `FormSchemaDocument` في الذاكرة) عبر Props، لا نسخة ثانية أو مصدر بيانات منفصل. `StudioOutline` لا يستدعي API خاصًا به إطلاقًا.
- **لا إعادة تحميل Schema كاملة بعد كل تعديل بسيط**: كل تعديل (سحب، تحرير عنوان، شرط، صيغة) يُطبَّق محليًا فورًا عبر `applySchema`/`historyStore`، ويُبَثّ للخادم فقط عبر Autosave المُدبَّس (800ms) — لا `refetch` لكامل الإصدار بعد كل تعديل. الاستثناء الوحيد المتعمَّد: بعد نجاح Autosave، تُبطَّل ذاكرة React Query المخبأة (`invalidateQueries`) لضمان اتساق `allowedActions`/الحالة عند إعادة الزيارة، لا إعادة جلب فورية إجبارية لكل حرف.
- **Undo history محدود**: `historyStore.ts` (غير مُعدَّل) يحدّ سجل التراجع بـ50 عملية (`MAX_HISTORY`)، يمنع تضخم الذاكرة غير المحدود.
- **Validation لا ينفذ Query لكل حقل**: التحقق نداء API واحد (`POST .../validate`) يعيد قائمة أخطاء لكامل الـSchema دفعة واحدة، ويُحلَّل محليًا (`locateIssue`, `classifyIssues`) بلا أي نداء إضافي لكل عنصر.

## ما لم يُقَس فعليًا (Missing — لا ادعاء اكتمال)

- **ميزانية موثَّقة لتحميل نموذج من 200 حقل**: لم يُنفَّذ اختبار أداء (Load test) فعلي يقيس زمن تحميل/استجابة الاستوديو لنموذج بهذا الحجم، ولا وُضِعت ميزانية زمنية رقمية موثَّقة (مثال: "أقل من Xms"). البنية (JSON واحد، لا حلقات استعلام) تدعم هذا الحجم نظريًا دون تغييرات إضافية، لكن هذا **لم يُختبَر تجريبيًا** في هذه الجلسة. **Missing**.
- **اختبار Query-count budget آلي**: لا اختبار تكامل جديد يقيس عدد استعلامات EF Core الفعلية المُنفَّذة عند تحميل الاستوديو أو حفظه (لا `DbCommandInterceptor` عدّاد مُضاف). الاطمئنان الحالي مبني على قراءة الكود (لا حلقات) لا قياس مباشر. **Missing**.
- **أداء Condition/Formula Builder مع عدد كبير من الحقول**: قوائم اختيار الحقل في `ConditionBuilder`/`FormulaBuilder` تُبنى بـ`flattenFields` بسيط (O(n))، وهذا كافٍ نظريًا لعشرات/مئات الحقول، لكن لم يُختبَر أداء إعادة الرسم (Re-render) الفعلي لواجهة React مع 200 حقل متزامن في DOM واحد.

## توصية لمرحلة لاحقة

إن كان حجم 200 حقل سيناريو حقيقيًا متكررًا، يُوصى بإضافة Virtualization لـ`StudioCanvas`/`StudioOutline` (مثل `@tanstack/virtual`) واختبار أداء مخصص قبل الاعتماد على هذا الرقم في بيئة إنتاج — خارج نطاق هذه المرحلة.

## طريقة المحافظة على Deep Links القديمة

- أي Route يتحول Redirect (الجدول أعلاه) يجب أن يبقى Route فعليًا عبر `<Navigate>` — **تصحيح دقيق**: هذا تنقّل داخلي من جهة العميل (Client-side navigation) وليس استجابة HTTP فعلية بحالة 301/302؛ لا يُصدِر الخادم/الـCDN أي رمز حالة تحويل حقيقي هنا. إن احتاج مستقبلاً ضمان دلالات HTTP 301/302 فعلية (لمحركات بحث خارجية مثلاً)، فهذا يتطلب إعداد تحويل منفصل على مستوى الخادم/الـCDN، خارج نطاق `<Navigate>` وخارج نطاق هذه الوثيقة. المهم للمستخدم النهائي: أي رابط محفوظ خارجيًا (بريد، Bookmark، إشعار قديم) يستمر بالعمل داخل التطبيق، بصرف النظر عن آلية HTTP تحته.
- أي Route يُدمَج ضمن Workspace (مثل `/notes/:id`) يجب أن يستمر يعمل كرابط دائم يفتح نفس تجربة الـPanel/Split View داخل الـWorkspace الجديدة (وليس صفحة اختفت تمامًا) — تحويل داخلي بصري، لا حذف مسار. **يجب أن يحدث هذا عند مستوى Route Resolver/إعادة التوجيه نفسه** (أي أن الـRoute يُحل تقنيًا إلى وجهة الـWorkspace الجديدة)، لا مجرد إخفاء رابط التنقّل (Nav) القديم مع بقاء الـRoute يعرض المكوّن القديم — إخفاء رابط تنقّل فقط لا يحمي من الوصول المباشر عبر Bookmark/إشعار/رابط خارجي.
- إشعارات محفوظة قديمة تحمل روابط لصفحات قد تُدمَج مستقبلاً (`/notes/:id`, `/corrective-actions/:id`) تبقى صالحة بنفس المبدأ أعلاه.

## طريقة الانتقال التدريجي

1. **لا Big Bang** — كل مرحلة (#143 ثم #144 ثم #145 ثم #146) تُنفَّذ وتُشحَن مستقلة، بحيث يبقى النظام قابلاً للاستخدام الكامل بين كل مرحلة والتي تليها.
2. **إبقاء الصفحات القديمة فعّالة حتى إثبات التغطية الكاملة للبديل** — لا حذف صفحة قديمة إلا بعد تأكيد (باختبارات تفاعل فعلية، لا افتراض) أن كل إجراء متاح فيها اليوم متاح في البديل الجديد.
3. **قياس الاستخدام قبل الحذف الفعلي** (راجع القسم التالي) — لا حذف Route قديم يحمل استخدامًا فعليًا مرصودًا دون تأكيد انتقال المستخدمين للبديل.

## Feature flags عند الحاجة

- يُقترَح استخدام نفس نمط `VITE_ENABLE_REFERENCE_WORKSPACE` الموجود فعليًا (env flag بسيط) لتفعيل الواجهة الجديدة تدريجيًا لمجموعة مستخدمين محدودة قبل التعميم الكامل، خصوصًا لـObservation Workspace الجديد نظرًا لحساسية استخدامه اليومي المرتفع.
- لا حاجة لنظام Feature Flag معقّد جديد (LaunchDarkly أو مكافئ) — النمط الموجود بالفعل في الكود (فحص `import.meta.env`) كافٍ لحجم هذا الانتقال.

## Compatibility مع APIs الحالية

- كل العقود المذكورة في تحليلات الفجوة الثلاثة (`observation-workspace-gap-analysis.md`, `form-designer-gap-analysis.md`, `form-operations-gap-analysis.md`) قابلة للاستهلاك من الواجهة الجديدة **دون تغيير Backend** إلا في حالتين موثَّقتين صراحة:
  1. إضافة `AllowedActions` لـ`CorrectiveActionDetailDto` (تحسين، لا كسر توافق — حقل إضافي اختياري).
  2. أي Endpoint جديد لدعم "صعّد الآن" الفوري لعنصر بعينه (ميزة جديدة، لا تعديل عقد قائم).
- **لا يجوز حذف أو تعديل أي Endpoint موجود** أثناء مرحلة الانتقال — الواجهة الجديدة تستهلك نفس العقود القديمة، والتغيير كله في طبقة العرض.

## طريقة عدم كسر النماذج والملاحظات الحالية

- أي ملاحظة/نموذج/حملة/استجابة موجودة اليوم في قاعدة البيانات يجب أن تُعرَض وتُدار بشكل صحيح في الواجهة الجديدة بلا استثناء أو Migration بيانات — التغيير واجهي بحت في هذه المرحلة وما بعدها مباشرة.
- إصدارات النماذج المقفَلة (Locked) يجب أن تستمر بالانفتاح والعرض الصحيح (كـSnapshot JSON على الأقل) بلا أي فقدان بيانات تاريخية.

## كيفية إزالة المكونات القديمة بعد اكتمال البديل

1. تأكيد التغطية الوظيفية الكاملة (اختبارات تفاعل تُثبت كل إجراء قديم متاح في الجديد).
2. تحويل Route القديم إلى Redirect (لا حذف فوري) لفترة مراقبة.
3. مراقبة أي استخدام متبقٍّ للمسار القديم (راجع قياس الاستخدام أدناه).
4. الحذف الفعلي للملف/المكوّن القديم فقط بعد فترة مراقبة كافية بلا استخدام يُذكَر.

## طريقة قياس الاستخدام قبل الحذف

**فجوة حالية**: لا توجد أداة Analytics/Telemetry لاستخدام الصفحات في الكود المدروس. قبل الحذف الفعلي لأي Route قديم، يجب أولًا إضافة قياس بسيط (حتى لو عداد استدعاء API بسيط في سجل التدقيق الموجود أصلاً `AuditLog`، أو سجل خادم للطلبات) لتتبّع من لا يزال يستخدم المسار القديم بعد إطلاق البديل — هذا يُدرَج كمتطلب تقني صغير ضمن أول PR تنفيذي من #143، لا كأداة منفصلة جديدة.

## Rollback strategy

- بما أن الانتقال تدريجي (Route بديل، لا استبدال فوري)، الـRollback بسيط بشرط تطبيقه في المكان الصحيح: **يجب أن يعمل الـRollback عند مستوى Route Resolver نفسه (تبديل الوجهة التي يُحل إليها الـRoute المدموج)، لا عند مستوى إخفاء رابط تنقّل فقط** — فبعد دمج الـRoutes وتوجيه Deep links/الإشعارات القديمة مباشرة لتجربة الـWorkspace الجديدة (كما ينص القسم أعلاه)، مجرد إخفاء رابط الشريط الجانبي لا يعيد المستخدمين الواصلين عبر Bookmark أو إشعار أو رابط خارجي إلى الصفحة القديمة. آلية الـRollback الفعلية: نفس نمط `VITE_ENABLE_REFERENCE_WORKSPACE` (Feature flag) يُستخدَم للتحكم في *وجهة الـResolver نفسها* (أي Route يُحل تقنيًا إلى المكوّن القديم أو الجديد)، مع إبقاء مكوّن الصفحة القديمة مسجَّلاً وقابلاً للعرض حتى انتهاء الحاجة للـRollback — لا مجرد التحكم في ظهور رابط تنقّل. لا يتطلب أي إجراء طارئ على قاعدة البيانات أو الـBackend في الحالتين — لأن لا تغيير في العقود يتطلب Rollback عكسي معقّد.
- **لا Rollback على مستوى قاعدة البيانات مطلوب في أي مرحلة من هذه الخطة** — كل التغييرات المخطَّطة واجهية، باستثناء الإضافة الاختيارية لحقل `AllowedActions` (توافقي بطبيعته، لا يكسر عملاء قدامى يتجاهلونه).
